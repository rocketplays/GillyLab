PRE-UFC TAPE ON FIGHT PASS — WHO HAS IT, AND WHERE
Generated 2026-07-20 while sourcing UFC 330. First pass, not exhaustive; read the
caveats at the bottom before trusting a "none".

WHY THIS FILE EXISTS
The per-fighter Fight Pass playlists ("Watch all of X's UFC fights here!") are
UFC-only by design. Everything placed in TAPE_STUDY for UFC 330 came from those,
so every pre-UFC bout on this card is still unlinked. Fight Pass does carry a lot
of that footage, but under a different naming scheme:

    <Promotion> Alumni: <Fighter>          e.g. "LFA Alumni: Chidi Njokuani"

Those are separate playlists with their own ids. They are the trail to follow.

HOW TO FIND THEM
  1. ufcfightpass.com/search, signed in
  2. Open Filter -> tick PLAYLIST (this matters: results paginate at 20 and a
     playlist can otherwise sit below the fold behind podcasts and full cards)
  3. Type the fighter's name; wait ~4s for the grid to settle
  4. The playlist id is in the DOM, not in an href:
         data-testid="card-container-PLAYLIST#28147"
  5. Open /playlist/<id>; the video tiles there ARE real <a href="/video/<id>">

THE SWEEP PROCEDURE — RUN ALL OF IT, EVERY CARD, NO EXCEPTIONS

  1. For each fighter: search their name with the PLAYLIST filter on, take the
     playlist whose title is their name (or "<Some Title>: <Name>" — champions get
     a prefix), harvest it.
  2. node scripts/place-tape-links.cjs <links.txt>          # report
  3. node scripts/place-tape-links.cjs <links.txt> --write  # apply + verify
  4. node scripts/place-tape-links.cjs --gaps <event-slug>  # PASS 2 — MANDATORY
  5. Search every line pass 2 prints. Place what you find. Re-run step 4.

STEP 4 IS NOT OPTIONAL AND THE SWEEP IS NOT FINISHED WITHOUT IT.
Measured over two cards: the playlists alone left 25 and 25 bouts unlinked; pass 2
recovered 6 and 6, EVERY ONE of which was already in the library. Playlists are
curated and incomplete, and DWCS bouts are never in them — on the Aug 22 card all
six recoveries were Contender Series fights.

  PASS 1  the fighter's playlist
  PASS 2  diff against their org=="UFC" rows and SEARCH EACH GAP INDIVIDUALLY

Query as "<Fighter> vs <Opponent>" — that ranks the bout first; the opponent's
name alone does not. Results cap at 20 with no pagination, so try both phrasings
before calling a video absent.

MATCH ON THE FULL OPPONENT NAME, NEVER THE SURNAME. Searching Jasudavicius vs
"Karine Silva" surname-matched the "Mayra Bueno Silva" video — wrong fight, and
one already placed. Surname matching does not fail loudly, it fails plausibly.

REMATCHES: PIN THEM, NEVER ORDER THEM. If a fighter met an opponent twice and only
one video exists, the script REFUSES to place it until you pin the meeting —
"Opponent @2023", or "Opponent @2016-01" when both meetings fall in one year. It
refuses because the old ordering assumption put three wrong links on live profiles
(Rodrigues/Ferreira, Gamrot/Parke, Lemos/Cantuária). Read the true date off the
video: ufcfightpass.com/video/<bare-id> or youtube.com/oembed — both work logged
out. Beware titles like "Gamrot vs Norman Parke 1 | KSW 53": that is the FIRST
meeting released as a promo for KSW 53, not the KSW 53 fight.

"KAUÊ FERNANDES" NAME MISMATCH — RAISED, THEN MEASURED, AND IT IS A NON-ISSUE

  data/event.json calls him       "Kauê Fernandes"   (with circumflex)
  FIGHT_HISTORY / FIGHTER_STATS   "Kaue Fernandes"   (without)

I flagged this as a probable bug of the "stephen erceg" kind and was wrong. Ran it
through the real resolver before adding an alias:

  feed row: "Kauê Fernandes"  slug "kaue-fernandes"  ->  resolves to "Kaue Fernandes"

resolveCanonicalFighterName() tries SLUGS FIRST, and the feed supplies
fighterSlug "kaue-fernandes", so it matches the FIGHTERS roster on the first key
and never reaches NAME_ALIASES. Independently, nameToSlug() already normalises the
circumflex away (NFD + combining-mark strip), so the name path resolves too.

No alias was added: it could never fire, and a dead entry in that table invites
the next person to assume the diacritic case is handled BY the alias rather than
by the slug, which is the wrong mental model to leave behind.

The general lesson for this file: a spelling difference between the feed and the
DB is only a bug if the lookup path actually uses the raw name. Check the resolver
before writing the alias.


CAVEATS — read before treating a blank as "no footage"

  1. THE ALUMNI SWEEP IS NOT COMPLETE. Several of these lookups ran with a 2.6s
     settle and without the PLAYLIST filter. That combination has already produced
     three false "none"s in one sitting: Barboza, Luque and Magny all appeared to
     have no playlist at all, and all three do — the cards were simply below the
     20-result fold. A blank in the alumni table above means "not found on a first
     pass", NOT "does not exist". Re-check with the filter on and a 4s+ wait.

  2. THE PLAYLIST TITLE IS NOT ALWAYS THE FIGHTER'S NAME. Champions get a prefix:
     "UFC Welterweight Champ: Islam Makhachev", "UFC Womens Strawweight Champion:
     Mackenzie Dern". Matching on an exact name misses those. Dern was reported as
     having no playlist for exactly this reason.

  3. A /video/ LINK THAT REDIRECTS TO /purchase IS NOT A BROKEN LINK. I first read
     this as "some premium videos need an extra purchase". Wrong on both counts.
     Measured 2026-07-20: FOUR videos spanning 2012 to 2025, including a regional
     Cage Warriors bout, ALL redirected to /purchase?from=%2Fvideo%2F<id> in a
     signed-in browser. A 2012 regional fight is not premium content, so it is not
     per-video entitlement — the account was registered but had no active
     subscription on it. Fight Pass separates the two states: a registered account
     browses playlists and search fine (which is why every harvest in this file
     worked), but plays nothing.

     So: never judge a link by whether it plays. Judge it by the OG metadata on
     ufcfightpass.com/video/<bare-id>, which is public and names the fighters and
     the date. And expect site visitors without a subscription to hit this wall on
     every Fight Pass link we publish — that is inherent to the source, not a bug.
