================================================================================
BET & CLV TRACKER — SCREENSHOT READER (SHIPPED 2026-08-25)
A third way to log a bet: upload a screenshot of the slip, a vision model reads
the legs, you confirm, it saves through the exact path a manual bet already uses.
Written 2026-08-19. Built and deployed 2026-08-25 — see sections 7 and 8 for
exactly what shipped and what it was tested against.

SHIPPED WITH ONE KNOWN OPEN GAP, ACCEPTED KNOWINGLY, NOT DISCOVERED LATE: no
screenshot tested so far has a real non-zero stake sitting near a dollar-
denominated reward badge (DK Crowns, FanDuel Reward Points) — the exact
collision the FanCash bug (sec 8) was about. Section 2's review-before-save is
the permanent backstop for this, same as for any other misread — watch the
first real reports of a wrong stake for a sign this needs tightening further.
================================================================================

--------------------------------------------------------------------------------
0. WHY THIS EXISTS / WHAT IT'S NOT
--------------------------------------------------------------------------------
The ask that started this: auto-log bets by linking a sportsbook account
(BetSync-style, e.g. SharpSports). Priced out — betSync starts at $500/mo for
0-99 linked accounts, $1,000/mo for 100-999, and there's no meaningfully cheaper
competitor in that specific niche (account-linking, not odds-feed APIs — the one
other product found, BtrBet, is itself built on SharpSports, not a competitor to
it). Rejected for now on cost, not feasibility.

This is the alternative: no linked accounts, no sportsbook credentials touch us
at all, ever. The user takes a screenshot of a slip they already placed and
uploads it; a vision model extracts the legs into the same fields the manual
"Log a bet" form already has. Requires ONE new Worker endpoint and a form
pre-fill step — no new infra, no new KV binding, no subscription.

Estimated cost at 100 users x 5-10 screenshots/week (see section 5): $7-45/month
depending on model choice. That's the number that makes this worth building
before anything BetSync-shaped.

--------------------------------------------------------------------------------
1. THE FLOW, END TO END
--------------------------------------------------------------------------------
  1. On the Bet & CLV Tracker's "Log a bet" tab, add a third entry mode next to
     the existing tracked/manual toggle: "Scan a screenshot."
  2. User drops/pastes/picks an image. Client-side: downscale to something
     reasonable (long edge ~1568px — see 4) before upload, both to keep the
     request small and because Claude will resize to that anyway.
  3. POST the image (base64) to a new endpoint, POST /api/bets/scan.
     Auth: same betsSession() gate as every other /api/bets/* route — logged in
     AND subscribed. This is not a free-tier feature; it costs real money per
     call and should be gated exactly like the rest of the tracker.
  4. Worker calls the vision model (see 4) with a prompt that asks for STRICT
     JSON matching the shape handleBetsAdd() already accepts:
       - kind guess: "manual" (single) or parlay (legs[])
       - per leg: match/matchup text, pick, market guess, odds
       - top-level: stake if visible, book name if visible (label only, see
         BET-TRACKER-ROADMAP.txt sec 3 "one sportsbook per parlay" — book isn't
         stored today; decide whether this feature is what finally adds it)
     No JSON, or JSON that fails validation -> return a "couldn't read this
     screenshot" error, NOT a half-filled guess. Never silently drop a leg.
  5. Response goes back to the client as a DRAFT, not a save. Pre-fill the
     existing manual/parlay form fields with it — reuse the UI that's already
     there, don't build a new one.
  6. Before the draft is shown, run each leg's matchup text through the same
     fuzzy matcher the tracked-bet path already uses (btFindBout in
     worker/index.js) so the UI can flag "this matches Kaik Brito vs Trent
     Miller on an upcoming card" if it does. If it matches AND the bout isn't
     decided yet, offer to log it as `kind: "tracked"` (verified, CLV-eligible)
     instead of manual — that's a real upgrade over typing it in by hand, since
     today tracked-vs-manual is the user's choice at entry time, and here the
     screenshot already told you which fight it is.
  7. User reviews the pre-filled draft on screen, corrects anything wrong,
     confirms. Submission is a normal POST /api/bets — same validation, same
     lock, same parlay correlation re-check that already exists. This feature
     changes NOTHING about what happens after confirm.

The governing rule from BET-TRACKER-ROADMAP.txt ("the client never decides
anything that matters") extends here as: the MODEL never decides anything that
matters either. It only ever produces a draft a human confirms.

--------------------------------------------------------------------------------
1B. BATCH UPLOAD — MULTIPLE SCREENSHOTS, ONE STEPPER (added 2026-08-24)
--------------------------------------------------------------------------------
Discussed after the v1 flow above: instead of one screenshot -> one draft ->
back to the upload button for the next one, let the user pick/drop N images
at once and step through the drafts one at a time without re-uploading.

THIS DOES NOT CHANGE THE BACKEND. No batch endpoint. The client still calls
POST /api/bets/scan once per image — just N times instead of once, a few
in flight at a time (e.g. 3 concurrent) so it doesn't serialize into a slow
queue but also doesn't hammer the vision API. handleBetsScan() stays exactly
as specced in section 3, one image in, one draft out.

FLOW:
  1. User selects/drops N files in the "Scan a screenshot" mode.
  2. Client downscales each (same as section 1 step 2) and fires the scan
     calls, capped at ~3 concurrent.
  3. As each call resolves, its draft joins a queue in upload order. The
     review screen (section 1 step 5-7, unchanged) shows draft #1 as soon as
     it's ready — does NOT wait for all N to finish reading.
  4. User reviews/corrects/confirms draft #1 exactly as in the single-image
     flow. Confirm posts through the normal POST /api/bets path — nothing
     about the save changes. The form then advances to draft #2 automatically.
  5. If the position the user has reached is still being read, show a brief
     "reading..." state rather than blocking earlier drafts that are ready.
  6. Add a SKIP action next to Confirm, separate from "couldn't read this
     screenshot" — the user may have screenshots of old/cancelled bets or a
     book they don't track. Skip advances the queue with nothing written.
  7. Position indicator ("2 of 5") so the user can see progress through the
     batch.

WHY THIS IS SAFE TO ADD WITHOUT REOPENING SECTION 2's ARGUMENT: each draft
still gets its own individual human review and its own individual confirm.
Batching changes how many times the user re-opens the file picker, not
whether a human looks at each bet before it saves. The rule stays: the model
never decides anything that matters, only now it says so N times in a row.

OPEN DECISION ADDED HERE: the per-user daily rate cap (section 3, section 6)
now matters more, because a user can hit it in one batch instead of over a
week. The client should check remaining quota before firing the batch and
show up front which screenshots won't be scanned today ("5 of these won't be
scanned — daily limit"), rather than having them fail silently partway
through the queue.

--------------------------------------------------------------------------------
2. WHY REVIEW-BEFORE-SAVE IS NOT OPTIONAL
--------------------------------------------------------------------------------
Screenshots are messy in ways a linked-account API response never is:
  - Dark mode vs light mode books, different fonts/layouts per sportsbook.
  - Cropped screenshots (missing the stake, or missing which leg is which in a
    same-game parlay).
  - Boosted-odds banners, promo badges, and "odds boost" strikethrough prices
    sitting next to the real price — a model can misread which number is live.
  - Physical betting-kiosk receipts (different problem entirely: thermal-printer
    font, no home team highlighting, may not even be a book this app tracks).
  - Fighter name variants / nicknames the OCR reads correctly but that don't
    match FIGHTERS' canonical spelling — this is the SAME problem the app
    already solves elsewhere (NAME_ALIASES, nameToSlug) and should reuse it,
    not reinvent matching.
Auto-saving on a misread creates a bet the user didn't actually place, which
poisons record/ROI/CLV — the exact thing Phase 1's "verified vs self-reported"
split exists to prevent. A wrong auto-save is worse than no auto-save.

3. WHAT NEEDS TO BE BUILT
--------------------------------------------------------------------------------
worker/index.js
  - New route: POST /api/bets/scan (near the other /api/bets/* handlers).
  - New handler, e.g. handleBetsScan(): auth gate, decode image, call the
    vision model, validate + shape the JSON response, return draft (not saved).
  - Reuse btFindBout() for the "does this match a tracked bout" step (3.6
    above) rather than writing a second matcher.
  - New secret: an API key for whichever vision model is used (ANTHROPIC_API_KEY
    or similar) — `wrangler secret put`, same pattern as STRIPE_SECRET_KEY /
    RESEND_API_KEY already in wrangler.toml. No new KV binding needed.
  - Rate limit per user (e.g. N scans/day) — this is the one place a bug or an
    abusive script could run up a real bill quickly, unlike everything else in
    the tracker which is free to the operator. Cap it even generously (50/day
    is still $0.17-0.50/user/day worst case) rather than leave it open.

index.html
  - Third entry-mode button on the "Log a bet" tab: "Scan a screenshot."
  - Upload UI: file input + paste-image support. Client-side downscale before
    sending (canvas resize) — smaller upload, and no benefit to sending more
    pixels than the model will use anyway (see 4).
  - Draft review screen: pre-filled version of the existing manual/parlay form,
    editable, with a visible "matched to an upcoming card" indicator per leg
    when btFindBout hits.
  - Error state for "couldn't read this screenshot" — offer manual entry as the
    fallback, don't dead-end the user.

Nothing in FIGHT_HISTORY/ODDS_HISTORY/grading changes. Nothing in the KV
storage shape changes (still writes through the same POST /api/bets path).

--------------------------------------------------------------------------------
4. MODEL CHOICE + PROMPT SHAPE
--------------------------------------------------------------------------------
Model: Claude Haiku 4.5 for the first pass on every image — cheap, fast, and
reading a bet slip is a bounded extraction task, not a reasoning task. Retry
once on Sonnet ONLY if Haiku's response fails JSON validation or looks
malformed (e.g. a leg missing odds) — keeps the bulk of volume on the cheap
tier and only pays for the expensive one on the images that actually need it.

Image sizing: Claude resizes to a ~1568px long edge / ~1600 token cap before
reading, so there's no cost benefit to uploading a full-resolution photo of a
screenshot — downscale client-side to roughly that before sending.

Prompt should return ONLY a JSON object, schema-locked to what handleBetsAdd()
accepts today (see BET-TRACKER-ROADMAP.txt sec 1 for the 7 markets + PARLAY
shape). Explicitly instruct: if a field isn't visible or legible, omit it /
mark it uncertain rather than guessing a plausible-looking value — a guessed
stake or odds is worse than a blank one the user has to fill in.

--------------------------------------------------------------------------------
5. COST (see chat for the full derivation — summary here)
--------------------------------------------------------------------------------
At 100 users x 5-10 screenshots/week (~2,200-4,300 images/month):
  Haiku 4.5 (~1600 img tokens + ~300 prompt + ~300 output):  ~$0.0034/image
      -> ~$7-15/month  (~$90-180/year)
  Sonnet 4.6 (same token shape):                             ~$0.0102/image
      -> ~$22-44/month (~$265-530/year)
Even the Sonnet ceiling is roughly 10x cheaper than betSync's $500/mo floor at
the same user count, and it scales with actual usage instead of jumping in
$500 steps at fixed account-count tiers. Add the per-user rate cap (sec 3) as
the hard ceiling on a worst-case bill.

6. OPEN DECISIONS — RESOLVED 2026-08-24, BUILT AGAINST THESE ANSWERS
--------------------------------------------------------------------------------
[x] Image storage: NO. handleBetsScan() passes the image to the model and
    discards it — never written to KV/R2. Not revisited; no debugging need
    has come up.
[x] `book` field: ALREADY EXISTED. handleBetsAdd() (line ~890) already reads
    body.book as free text, no schema change needed — the roadmap note that
    raised this was stale. handleBetsScan()'s draft populates the same field.
[x] Per-user rate limit: 25/day (BT_SCAN_DAILY_CAP), tracked via a
    date-keyed PICKS key (btscancap:<email>:<date>, 2-day TTL) — no new KV
    binding. Loosen later if it's ever actually hit.
[x] Same-game-parlay / prop-heavy scope, AND the market-code question this
    turned into once building started: a scanned bet is v1-scoped to ALWAYS
    log as self-reported ("manual"), through the exact POST /api/bets path
    Custom bet already uses — never auto-submitted as "tracked". Reason
    (found during the build, not anticipated here originally): mapping a
    screenshot's free-text market label onto the app's 9 BT_MARKETS codes
    reliably is its own real classification problem, and a wrong guess there
    would silently misfile a bet as CLV-eligible when it isn't — exactly the
    kind of "the model decided something that mattered" this whole plan
    exists to prevent. A matched leg (server-side name match against
    /data/event.json, same normalization as btBoutDecided) shows as an
    INFORMATIONAL badge only — "matches an upcoming card" — and does not
    change what gets submitted. Upgrading matched legs to real "tracked"
    bets with correct market codes is a real follow-up, not done here.
[x] Max batch size: 12 (BT_SCAN_MAX_BATCH), enforced client-side in
    btScanPickFiles() before any scans fire.

8. PROTOTYPE RESULTS (2026-08-24) — SCHEMA VALIDATED, TWO REAL BUGS FOUND
--------------------------------------------------------------------------------
Ran the section-4 schema against 9 real screenshots (3 sportsbooks, singles,
2/4/5-leg parlays, a $0-placeholder wager field, a promo-currency badge) plus
1 deliberately non-bet-slip image. Script: scan_prototype.py (not committed —
prototype only, per the "outside the app first" instruction this section used
to carry). Final result: 9/9 valid, correct JSON. Two real bugs surfaced and
one is now baked into the prompt below; the other is already covered by an
existing plan step.

BUG 1 — REWARD CURRENCY READ AS STAKE. FOUND BY THE OWNER, NOT THE TEST.
The first pass read a Fanatics "FanCash $0.25" badge (loyalty/reward currency,
not money risked) as the bet's stake — confidently, with nothing flagged in
uncertain_fields. This is worse than the "$0 placeholder" case section 4
already guards against: that one is obviously fake, this one looks like a
real, small, plausible stake. It would have sailed through a distracted
review. FIXED by adding an explicit rule: stake only comes from a field
labeled "Wager"/"Risk"/"Bet Amount"/an amount the user typed, and reward-
currency labels ("Cash", "FanCash", "DK Dollars", "Bonus Bets", "Odds Boost
Token") are never the stake even when a dollar figure sits right next to
them. Re-tested on the same image: stake now correctly null, flagged in
uncertain_fields. Regression-tested against all 9 images after the fix — no
other extraction changed.
LESSON: "plausible-looking and confident" is a worse failure than "flagged
uncertain" — the review-before-save screen (section 2) is the backstop for
the second kind, not the first. Any field that can be confused with a
similar-looking but wrong number needs its own explicit exclusion rule in the
prompt, not a hope that the model infers it. Sportsbook UIs put reward
currency, odds-boost banners, and promo badges in exactly the visual position
a real stake would occupy — this will recur with other fields as more books
get tested, not just stake.

BUG 2 — NAME MISREAD: "Jamall Emmers" READ AS "Jamalii Emmers". One letter,
one image, out of ~9 fighter names read correctly elsewhere. This is not a
new problem — it is the exact failure mode section 1 step 6 and section 2
already name ("fighter name variants... this is the SAME problem the app
already solves elsewhere, NAME_ALIASES / nameToSlug — reuse it, don't
reinvent matching"). NOT independently fixed here; this is the reason
btFindBout() must run on every leg before anything is treated as a confirmed
match, not an optional nice-to-have.

WHAT WORKED WITHOUT CHANGES:
  * "Omit rather than guess" held on stake, book, and per-leg odds across
    every image where those fields genuinely weren't visible — including a
    parlay slip that shows only the total odds, not each leg's, which the
    model correctly left null rather than backing out a plausible split.
  * Book name extraction worked cleanly off a visible logo (Fanatics), and
    stayed null on every cropped/logo-less image rather than guessing.
  * The non-bet-slip rejection path returned the exact "not a bet slip"
    shape from section 4, not a malformed guess.
  * A verbatim app-side typo ("By y KO/TKO/DQ") was transcribed exactly
    rather than "corrected" — the extraction is not supposed to clean up
    what's on screen, and it didn't.

ONE THING THIS PROTOTYPE COULDN'T TEST: the "no markdown fences" instruction
in the prompt was ignored 100% of the time (9/9 responses wrapped in ```json
fences) — cosmetic, not a data problem, but handleBetsScan() MUST strip
fences before calling JSON.parse/validation or every real response will fail
validation and route to the "couldn't read this screenshot" error path by
mistake. scan_prototype.py's strip_fences() shows the normalization needed;
port that logic into the worker handler, don't assume the model will comply
with the fence instruction just because it's asked to.

COST, MEASURED NOT ESTIMATED: 9 images, ~1,380 input / ~155 output tokens
each on Haiku 4.5 -> ~$0.0022/image, ~$2.17 per 1,000 images. Below the
section-5 estimate of ~$0.0034/image, and well inside the $7-45/month range
at the stated volume even before any Sonnet-retry escalation.

2026-08-25 UPDATE — first real upcoming-card screenshots (today's DWCS,
Galanti v Petruzzella, Fanatics). Both read correctly: matchup/pick/market/
+200 odds right on both. One had a "REWARDS · 40 PTS PENDING" badge (points,
not dollars) — correctly ignored, stake stayed null. The other had a genuine
blank "WAGER $" input — correctly read as null rather than guessing $0 or any
other value. Neither closes the gap below: still no screenshot yet with a
REAL non-zero stake typed into a wager field sitting near a dollar-
denominated reward badge (DK Crowns, FanDuel Reward Points) — that specific
collision still hasn't occurred in anything sent so far. Good signal, not yet
a closed loop.

GAP THIS PROTOTYPE COULD NOT CLOSE, AND WHY IT'S NOT A BLOCKER. After bug 1
(sec above), the stake rule was broadened from a named list ("FanCash", "DK
Dollars"...) to a pattern ("any branded currency/point/token distinct from
cash, even unrecognized ones, is never stake"). All 9 images still behave the
same after the broadening — no new false positives. But NONE of the 9 test
images contain a real dollar amount in an actual "Wager" field — every one is
either no-stake, a $0 placeholder, or the FanCash badge. So the broadened
rule is confirmed not to break on what we have, but it is NOT yet confirmed
to correctly keep a REAL stake when one is genuinely present next to a
DK Crowns / FanDuel Reward Points badge, which is exactly the ambiguity it
exists to resolve. Old screenshots can't test this — a placed bet on a past
event doesn't produce a fresh wager screen with live promo-currency chrome
the way an upcoming-card slip does. NOT A BUILD BLOCKER: section 2's
review-before-save is permanent, not a launch-day gate, so a wrongly-nulled
real stake is caught on the draft screen the same way a wrongly-read one
would be. Treat this as a standing to-do: the first real screenshots from an
upcoming card (ideally one DK or FanDuel slip with Crowns/Reward Points
visible near an actual wager) should be run through scan_prototype.py before
trusting the stake field's behavior, not assumed correct from this pass.
